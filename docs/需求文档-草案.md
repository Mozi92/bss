## 1. 项目概述

### 1.1 项目背景

乙方目前经营膳食类产品，以线下推广为主，拥有人脉资源及成熟渠道。现计划通过微信小程序搭建线上推广平台，实现线上线下一体化运营。甲方负责技术开发与维护，乙方负责运营推广。

### 1.2 项目目标

- 开发一款膳食类产品推广小程序，支持产品展示、在线订购、订单管理、积分兑换
- 实现33复制模式推广裂变体系
- 支持微信转发分享自动绑定推荐关系
- 建立完善的后台管理系统，支持产品、订单、用户、推广、兑换等全流程管理
- 实现甲乙方收益分配的透明化管理


## 2. 用户角色定义

| 角色 | 说明 | 使用端 |
|------|------|--------|
| **普通用户** | 浏览产品、下单购买、查看个人中心 | 小程序端 |
| **推广者** | 普通用户基础上，满足升级条件后获得推荐资格，可推荐新用户并获取推广奖励积分 | 小程序端 |
| **顶层节点** | 无推荐人的用户，自动成为推广体系中的一个顶层节点 | 小程序端 |
| **乙方运营人员** | 产品管理、订单处理、兑换审核与打款、数据查看 | 后台管理端 |
| **甲方技术人员** | 系统配置、规则配置、数据维护、Bug修复 | 后台管理端 |


## 3. 用户角色升级规则

### 3.1 推广者升级条件

| 规则项 | 说明 |
|--------|------|
| 升级条件 | 普通用户累计购买 **6件** 商品（已确认收货且未退款），**不区分订单数** |
| 升级方式 | 系统自动升级，无需手动申请 |
| 升级后权限 | 获得推广资格，可推荐最多 **3位** 新用户 |
| 升级通知 | 小程序端推送升级通知，提示用户获得推广资格 |

### 3.2 升级条件补充说明

| 场景 | 是否计入升级 |
|------|-------------|
| 单笔订单购买1件 | ✅ 计入1件 |
| 单笔订单购买6件 | ✅ 计入6件，**直接完成升级** |
| 单笔订单购买10件 | ✅ 计入10件，**超额完成升级** |
| 多笔订单累计6件 | ✅ 计入6件，累计完成升级 |
| 全额退款订单中的商品 | ❌ 不计入 |
| 部分退款订单中的商品 | 按实际保留件数计入（退款50%即计50%件数，向下取整） |
| 待付款/待发货/待收货状态 | ❌ 不计入，需确认收货后计入 |
| 已确认收货且未退款 | ✅ 计入 |

### 3.3 顶层节点规则

| 规则项 | 说明 |
|--------|------|
| 定义 | 注册时 **无推荐人**（非通过推广链接/二维码/分享进入）的用户 |
| 身份 | 自动成为推广体系中的一个 **顶层节点** |
| 权限 | 顶层节点即为推广者身份，无需满足升级条件 |
| 推荐权限 | 可直接推荐最多 **3位** 新用户 |
| 层级位置 | 位于推广体系的最顶端，无上级节点 |
| 间推终点 | 间推奖励逐层向上分配时，到达顶层节点后停止，剩余件数不再分配 |
| 备注 | 方案A下，乙方可将甲方指定账号设为顶层节点 |

## 5. 微信转发分享推广机制

### 5.1 转发分享绑定原理

| 项目 | 说明 |
|------|------|
| 绑定方式 | 推广者通过微信 **转发小程序** 给好友/群，好友点击进入后自动绑定推荐关系 |
| 技术实现 | 小程序转发时携带推广者的唯一标识参数，新用户首次进入时解析参数并绑定 |
| 适用场景 | 转发小程序卡片、分享到微信群、分享到朋友圈（如支持） |
| 推广码补充 | 除转发分享外，推广者仍可生成专属推广二维码/链接，两种方式等效 |

### 5.2 转发分享场景覆盖

| 转发场景 | 绑定方式 | 说明 |
|----------|----------|------|
| 转发小程序卡片 | 自动绑定 | 好友点击卡片进入小程序，自动解析携带的推广者标识 |
| 分享产品详情页 | 自动绑定 | 分享产品页面时携带推广者标识，好友进入后绑定 |
| 分享推广中心页 | 自动绑定 | 推广者主动分享推广页面 |
| 生成海报分享 | 自动绑定 | 生成带二维码的推广海报，扫码进入后绑定 |
| 朋友圈分享 | 自动绑定 | 如微信开放小程序朋友圈分享能力 |

### 5.3 转发绑定规则

| 规则项 | 说明 |
|--------|------|
| 绑定触发条件 | 新用户 **首次进入小程序** 时解析转发参数并绑定推荐关系 |
| 已注册用户 | 已注册用户通过分享进入，**不改变**已有推荐关系 |
| 多级转发 | 转发链路中的最后一层推广者获得绑定（即直接分享者） |
| 绑定优先级 | 转发分享参数 > 推广码参数 > 无推荐人（成为顶层节点） |
| 推荐人资格 | 绑定人必须为推广者身份（含顶层节点），普通用户无分享绑定权限 |
| 绑定后不可变更 | 推荐关系一旦建立，不可自行变更（特殊情况由后台处理） |

## 6. 积分体系设计

### 6.1 积分账户结构

每个用户的积分账户分为 **可结算积分** 和 **冻结积分** 两部分：

| 积分类型 | 说明 | 可兑换 | 可查看 |
|----------|------|--------|--------|
| **可结算积分** | 已超过退款保护期，确认不会因退款被扣回的积分 | ✅ 可申请兑换 | ✅ |
| **冻结积分** | 尚在退款保护期内，可能因退款被扣回的积分 | ❌ 不可兑换 | ✅ |
| **总积分** | 可结算积分 + 冻结积分 | — | ✅ |

### 6.2 退款保护期规则

| 规则项 | 说明 |
|--------|------|
| 保护期时长 | **7天**（自订单确认收货之日起计算，可配置） |
| 冻结开始 | 订单支付成功、推广奖励积分发放时，积分进入 **冻结状态** |
| 解冻条件 | 订单确认收货后 **满7天** 且未发生退款，冻结积分自动转为可结算积分 |
| 退款冻结处理 | 保护期内发生退款，按退款比例从冻结积分中扣除 |
| 逾期退款 | 超过7天保护期的退款申请，需乙方审核确认后从可结算积分中扣除（如可结算积分不足则记录负余额） |

### 6.3 积分状态流转

```
订单支付成功
     ↓
推广奖励积分发放（冻结状态）
     ↓
用户确认收货
     ↓
┌─── 7天保护期 ───┐
│                    │
│  保护期内退款？     │
│   ├─ 是 → 按比例扣除冻结积分 → 剩余冻结积分继续冻结至期满
│   └─ 否 → 7天后自动解冻
│                    │
└────────────────────┘
     ↓
冻结积分 → 可结算积分
     ↓
用户可申请兑换
```

## 9. 核心业务流程

### 9.1 用户注册与推荐关系绑定流程

```
新用户进入小程序
        ↓
判断是否通过转发分享/推广码进入
        ↓
  ┌─────┴─────┐
  是            否
  ↓             ↓
解析推广者标识  自动成为顶层节点
  ↓             ↓
绑定推荐人      获得推广者身份
  ↓             ↓
判断推荐人名下 推荐用户数量
  ↓
  < 3位 → 直接挂靠在推荐人名下
  ≥ 3位 → 由系统自动分配至已有下级名下
        ↓
注册完成，推荐关系确立
```

### 9.2 推广者转发分享流程

```
推广者进入小程序
        ↓
选择转发目标（小程序首页/产品页/推广中心）
        ↓
系统自动在分享路径中附加推广者唯一标识
        ↓
转发至微信好友/群
        ↓
好友点击进入小程序
        ↓
系统解析推广者标识
        ↓
判断好友是否已注册
  ├─ 已注册 → 不改变原推荐关系
  └─ 未注册 → 自动绑定推荐关系
              ↓
         好友注册成为推广者的推荐用户或由系统分配挂靠
```

### 9.3 普通用户升级推广者流程

```
普通用户下单购买
        ↓
订单支付 → 发货 → 确认收货
        ↓
系统统计有效购买件数（按商品件数累计）
        ↓
累计购买 ≥ 6件？
  ├─ 否 → 继续累计，展示升级进度（已购X件/6件）
  └─ 是 → 自动升级为推广者
              ↓
         系统通知用户
              ↓
         开通推广中心功能
              ↓
         生成推广码及转发分享能力
              ↓
         获得推荐新用户权限（最多3位）
```

### 9.4 下单与推广奖励发放流程（含冻结机制）

```
推广者的推荐用户下单 → 微信支付成功
        ↓
系统触发推广奖励计算引擎
        ↓
┌─────────────────────────────────┐
│ 直推奖励计算：                   │
│ 订单总金额 × 直推比例             │
│ 分配给推荐人                     │
│ 前提：推荐人具有推广者身份        │
└─────────────────────────────────┘
        ↓
┌─────────────────────────────────┐
│ 间推奖励计算：                   │
│ 从第1件开始，逐件向上分配          │
│ 第1件 → 最近的非推荐人层级        │
│ 第2件 → 继续向上（跳过推荐人）    │
│ ...直到顶层或件数用完             │
│ 前提：层级节点需为推广者身份       │
└─────────────────────────────────┘
        ↓
奖励积分发放到对应推广者账户
        ↓
积分进入【冻结状态】
        ↓
记录奖励流水（类型：冻结发放）
```

### 9.5 积分解冻流程

```
订单确认收货
        ↓
系统记录确认收货时间
        ↓
进入7天退款保护期倒计时
        ↓
┌─── 7天保护期内 ───┐
│                    │
│  发生退款？         │
│   ├─ 是 → 按退款比例扣除冻结积分
│   │       ↓
│   │   剩余冻结积分继续冻结至期满
│   │       ↓
│   │   记录积分扣减流水
│   │
│   └─ 否 → 等待期满
│                    │
└────────────────────┘
        ↓
7天期满，冻结积分自动转为可结算积分
        ↓
记录积分解冻流水
        ↓
用户可申请兑换
```

### 9.6 退款与积分扣减流程

```
用户申请退款
        ↓
乙方审核通过
        ↓
系统原路退回支付款
        ↓
系统自动计算需回收的推广奖励积分
        ↓
判断积分状态：
  ├─ 冻结积分充足 → 从冻结积分中扣除
  ├─ 冻结积分不足 → 先扣冻结，再扣可结算
  └─ 可结算也不足 → 记录负余额，后续获得积分时优先抵扣
        ↓
同时重新校验该用户的推广者升级条件
（重新统计有效购买件数，如不足6件，自动撤销推广者资格）
        ↓
记录积分扣减流水及资格变更记录
```

### 9.7 兑换流程

```
用户提交兑换申请
        ↓
系统校验可结算积分是否充足
        ↓
  ├─ 不足 → 提示用户可结算积分不足
  └─ 充足 → 冻结对应可结算积分
              ↓
         后台生成待审核记录
              ↓
         乙方运营人员审核
              ↓
  ├─ 驳回 → 解除冻结 → 通知用户
  └─ 通过 → 乙方线下转账打款
              ↓
         后台标记"已打款"
              ↓
         扣除可结算积分
              ↓
         用户端显示"已完成"
```


## 10. 推广奖励计算规则（技术规格）

### 10.1 直推奖励计算规格

| 项目 | 规格 |
|------|------|
| 触发条件 | 订单支付成功，且推荐人具有推广者身份 |
| 计算基础 | 订单实付总金额 |
| 计算方式 | 订单实付金额 × 推荐人名下序号对应比例 |
| 比例配置 | 第1位：20%，第2位：20%，第3位：60%（可配置） |
| 奖励对象 | 当前下单用户的推荐人 |
| 是否受挂靠影响 | 否 |
| 发放状态 | 冻结状态（进入退款保护期） |
| 退款处理 | 按退款比例从冻结积分中扣除 |

### 10.2 间推奖励计算规格

| 项目 | 规格 |
|------|------|
| 触发条件 | 订单支付成功，且层级节点具有推广者身份 |
| 计算基础 | 按订单内产品件数 |
| 计算方式 | 每件30积分（可配置），逐件向上分配 |
| 分配规则 | 从当前用户上一层开始，跳过推荐人层级 |
| 奖励对象 | 非推荐人的挂靠层级节点（需为推广者身份） |
| 是否受挂靠影响 | 是 |
| 发放状态 | 冻结状态（进入退款保护期） |
| 退款处理 | 按退款比例从冻结积分中扣除 |
| 终止条件 | 到达顶层节点或件数分配完毕 |

### 10.3 间推跳过逻辑说明

间推奖励计算采用 **逐层向上遍历** 的方式，具体逻辑如下：

1. 从当前下单用户的 **上一层挂靠节点** 开始检查
2. 如果当前检查的节点 **等于** 推荐人，则 **跳过该节点**，继续检查更上一层
3. 如果当前检查的节点 **不等于** 推荐人，且该节点具备推广者身份，则将本件产品的间推奖励积分（30积分）分配给该节点
4. 如果当前检查的节点 **不具备推广者身份**（普通用户），则继续向上检查
5. 分配完一件后，从该节点的上一层继续检查下一件
6. 重复上述过程，直到 **产品件数分配完毕** 或 **到达顶层节点**
7. 如果到达顶层节点后仍有剩余件数，剩余部分不再分配，归入平台收益

## 12. 技术架构

### 12.1 整体架构说明

系统采用 **前后端分离** 架构，分为三个主要部分：

| 层级 | 说明 |
|------|------|
| **小程序端** | 面向普通用户和推广者，提供产品浏览、下单购买、转发分享、推广中心、积分兑换等功能 |
| **后台管理端** | 面向甲方技术人员和乙方运营人员，提供产品、订单、用户、推广体系、积分管理、兑换审核、数据统计等管理功能 |
| **服务端** | 提供统一API接口，处理业务逻辑、数据存储、支付集成、推广奖励计算引擎、积分解冻定时任务、分享参数解析等核心能力 |

服务端按业务模块划分为：用户服务、产品服务、订单服务、推广奖励服务、分享推广服务、积分管理服务、兑换服务、数据统计服务。各模块通过统一的API网关对外提供服务，网关负责认证鉴权、限流和日志记录。

数据层采用关系型数据库存储核心业务数据，缓存层用于存储热点数据和会话信息，文件存储用于保存产品图片等静态资源。系统需包含 **定时任务调度模块**，用于处理积分自动解冻等周期性任务。

### 12.2 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 小程序前端 | **uni-app** | 跨平台开发框架，支持微信小程序及多端扩展，支持转发分享功能 |
| 后台前端 | **Blazor** | 基于.NET的Web应用框架，与后端技术栈统一 |
| 后端框架 | **.NET（ASP.NET Core）** | 与Blazor同技术栈，便于统一开发和维护 |
| 数据库 | PostgreSQL | 关系型数据存储，成熟稳定 |
| 缓存 | Redis 7 | 会话管理、热点数据缓存、推广标识缓存 |
| 定时任务 | Hangfire 或 .NET BackgroundService | 积分解冻等定时任务调度 |
| 文件存储 | 腾讯云COS或阿里云OSS | 产品图片、推广海报等静态资源 |
| 支付 | 微信支付API v3 | 小程序支付标准接口 |
| 部署 | Docker + Nginx | 容器化部署，便于运维 |

## 16. 风险与注意事项

| 风险项 | 说明 | 应对措施 |
|--------|------|----------|
| 微信审核风险 | 含推荐奖励机制的小程序需注意微信审核合规要求 | 提前准备合规说明，避免敏感表述 |
| 资金安全 | 积分兑换涉及线下转账 | 乙方严格审核，建立打款记录台账 |
| 规则争议 | 奖励计算规则复杂，用户可能误解 | 小程序端展示规则说明，客服解答 |
| 升级规则争议 | 用户可能对6件升级门槛有异议 | 提前公示升级规则，展示升级进度 |
| 退款导致降级 | 退款后撤销推广资格可能引发不满 | 明确规则说明，设置合理缓冲期 |
| 顶层节点过多 | 无推荐人用户过多导致推广体系碎片化 | 合理引导新用户通过推广链接注册 |
| 自动分配争议 | 第4位用户自动分配可能引发推广者不满 | 提前公示分配规则，确保系统公平分配 |
| 数据安全 | 用户数据泄露风险 | 权限控制、数据脱敏、操作审计 |
| 退款纠纷 | 奖励积分回收可能导致推广者负余额 | 明确负余额处理规则 |
